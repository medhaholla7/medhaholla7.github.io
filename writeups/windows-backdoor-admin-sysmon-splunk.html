Home SOC Lab Part 2: Detecting a Backdoor Admin Account on Windows

Medha Holla · Detection engineering · Tools: VirtualBox, Windows 11 Enterprise, Sysmon, Splunk Universal Forwarder, Splunk Enterprise

Summary. I added a Windows 11 machine to my home SOC lab, logged its activity with Sysmon, and sent the logs to Splunk using the Splunk Universal Forwarder. I then simulated an attacker creating a backdoor admin account, and Splunk caught it through Windows events 4720 (account created) and 4732 (added to Administrators), while Sysmon recorded the exact commands used.

Attack technique: Create Account: Local Account (MITRE ATT&CK T1136.001).

This builds on Part 1, where I set up Splunk and detected an SSH brute-force attack on Linux.

1. Lab setup

The forwarder sends logs to my laptop on port 9997, and a VirtualBox port forward passes them into the SIEM VM.

2. The attack

I played an attacker who already has access to the Windows machine (for example, after a phishing email). Using Windows' built-in net command, I created a new local user called backdoor and added it to the Administrators group.

Attackers do this for persistence: a hidden admin account lets them get back in later with full control, even if the original way in is closed.

3. Detection

Windows Security log

Two event codes showed exactly what happened:

  • 4720: a user account was created (backdoor)
  • 4732: a user was added to a security group (Administrators)
index=windows (EventCode=4720 OR EventCode=4732)

Sysmon

Sysmon's process events (Event ID 1) recorded the exact commands, who ran them (Analyst) and when. Each net command also appeared as a second process, net1.exe, which net.exe launches behind the scenes.

Alert

I saved a search for event 4732 with the Administrators group as a scheduled Splunk alert, New Local Admin Added, so any new admin account triggers a high-severity alert automatically.

index=windows EventCode=4732 Group_Name=Administrators

4. If this were real: response

  1. Verify: check with IT whether anyone legitimately created the account. No ticket or approval means treat it as an attack.
  2. Contain: disable the account straight away, and isolate the computer from the network if needed.
  3. Investigate: find out how the attacker got in. Check who ran the commands, what else that user did, and any logins around the same time.
  4. Remove: delete the backdoor account and any other changes the attacker made.
  5. Improve: limit who has admin rights, and keep the alert running.

5. Problems I hit and how I solved them

  • VMs were extremely slow and froze. Windows' Virtualization-Based Security forced VirtualBox into a slower mode, and resuming VMs from a saved state made them hang. Fix: shut VMs down properly instead of saving state, booted them fresh, switched WIN11's graphics controller to VMSVGA, and closed heavy apps (Chrome alone was using 4.4 GB of RAM).
  • Windows setup stalled on updates. Fix: disconnected the VM's network during setup, then set the connection as metered so updates wouldn't download in the background.
  • No copy-paste between my laptop and the VM. Fix: installed VirtualBox Guest Additions and turned on the shared clipboard.
  • The forwarder sent Security logs but not Sysmon logs. The forwarder runs as a limited service account that couldn't read the Sysmon log. Fix: added it to the Event Log Readers group, giving it only the rights it needed (least privilege).
  • Sysmon logs arrived as raw XML with no searchable fields. Fix: wrote a Splunk field extraction (props.conf and transforms.conf) that turns each XML data field into a searchable Splunk field.
  • Commands failed with "Access denied". They needed an administrator terminal. A reminder that admin rights are exactly what attackers go after.

6. What I learned

  • How Sysmon works: it records the detail normal Windows logs miss, like the exact command that ran, who ran it, and what launched it. That's what lets you see how an attack happened, not just that something changed.
  • How to spot and prevent backdoor accounts: a new admin account is a red flag, and events 4720 and 4732 catch it. To prevent it, limit who has admin rights, review admin group members regularly, and alert on any new admin automatically.
  • Getting logs into a SIEM is half the work. Permissions, field parsing and networking all had to be right before a single detection could work.
