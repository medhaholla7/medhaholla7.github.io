Android App Security Assessment: Amaze File Manager

Medha Holla · Mobile application security · Tools: source review, androguard, keytool, Python (cryptography), OWASP Mobile Top 10

Summary. I did a source-level security assessment of Amaze File Manager, a popular open-source Android file manager (version 3.11.3, the current release). I found four real issues in the shipped code, including a cryptographic flaw I proved with a working demo, and mapped each to the OWASP Mobile Top 10 with a concrete fix.

Scope and ethics: the app is open source. I reviewed public source code only, and the one proof-of-concept runs against my own test data, never anyone's files or device. Two older published CVEs were checked and are already fixed in this version.

I chose a real, widely used app rather than a deliberately vulnerable practice app, so the findings are genuine. Amaze has millions of installs and its source is on GitHub, which makes it a fair and legal target for review.

1. How I approached it

I worked from the app's manifest outward, the same order an attacker would:

  • AndroidManifest: which components are exported (reachable by other apps), and which permissions the app holds.
  • Each exposed feature: the built-in FTP server, the database viewer, the file-encryption feature.
  • The cryptography: how files and saved passwords are encrypted, and how TLS keys are stored.
  • Known history: the app's past CVEs, to check they were actually fixed.

Finding 1: the same encryption IV for every file (proven)

Amaze lets you encrypt a file with AES in GCM mode. GCM needs a number used once, called an IV or nonce, that must be different every time you encrypt with the same key. Amaze uses a single fixed IV hardcoded in its build config, so every file is encrypted with the same key and the same IV. The maintainers even left a note in the code: "TODO: Generate a random IV every time."

Reusing a GCM IV is a well-known break. If an attacker has two files you encrypted and can guess part of one (for example a standard file header), they can recover the matching part of the other without the key. I wrote a short demo, on my own invented data, that does exactly this:

KEY = AESGCM.generate_key(256)
IV  = b"<the app's fixed 12-byte IV>"   # same value for every file

c1 = AESGCM(KEY).encrypt(IV, known_file,  None)
c2 = AESGCM(KEY).encrypt(IV, secret_file, None)

# same key + same IV = same keystream, so:
#   c1 XOR c2 == plaintext1 XOR plaintext2
recovered = bytes(a ^ b ^ p for a,b,p in zip(c1, c2, known_file))
# -> prints the secret file's contents, no key needed

The demo recovers the "secret" file exactly. When I change it to use a fresh random IV per file, the same attack produces only garbage, which is the point.

Fix: generate a random IV for each file and store it alongside the ciphertext, which is the standard pattern and exactly what the code's own TODO asks for.

Finding 2: a "secret" TLS key that cannot be secret

Amaze can serve files over FTPS (encrypted FTP). The TLS private key for that lives in a keystore file shipped inside the app, and the password that unlocks it is written in plain text in the app's public build config. I confirmed the password opens the keystore and that it holds a real private key.

The deeper issue is not the weak password. It is that a private key bundled in every copy of an app can never be secret: anyone can pull it from the APK. That means the FTPS certificate is shared by every install and gives little real proof of which server you are talking to, so it does not protect against a man-in-the-middle on the network as a proper certificate would.

Fix: generate a unique key pair on each device at first run and keep the private key in the Android Keystore, which never exposes the raw key to the app or the APK.

Finding 3: anonymous FTP with write access by default

The built-in FTP server is handy for moving files over Wi-Fi, but when no username is set it enables anonymous login and grants write permission to the shared folder. On a shared or public network, anyone who finds the port can read and drop files in that folder without any credentials.

Fix: require a username and password by default, and make read-only the default sharing mode.

Finding 4: broad attack surface

The app exports several components other apps can call directly, including a database viewer and a text editor, and it holds powerful permissions: manage all storage, query all installed packages, and install and delete packages. None of these is a vulnerability on its own, but each one widens what a malicious app or a single bug can reach, so they are worth keeping to the minimum.

Fix: export only what genuinely needs to be, protect sensitive exported components with a permission, and drop permissions the core features do not need.

3. Checking the known CVEs

Amaze has two published vulnerabilities from earlier versions: unrestricted control of the FTP server through intents (CVE-2020-35173), and code execution through the database viewer (CVE-2024-33469). I checked both against the current source. The FTP control actions are now guarded by a dangerous-level permission, and the database viewer validates its input path before opening it. Both are fixed. Confirming this matters just as much as finding new issues: it is how you tell a live risk from an old headline.

4. What I learned

  • The worst crypto bugs are rarely a broken algorithm. Amaze uses AES-GCM, a strong choice, and still breaks it by reusing the IV. How you use the primitive matters more than which one you pick.
  • "Secret" and "shipped in the app" cannot both be true. A key or password inside an APK is public.
  • Convenience features like FTP are where defaults do the damage. Anonymous and writable is easy to turn on and easy to forget.
  • An assessment is not just a list of bugs. Verifying that old CVEs are fixed, and proving a finding with a demo, is what makes it trustworthy.

5. Disclosure

All four findings sit in public source, and the IV issue is already flagged in the code's own comments, so this writeup describes design weaknesses rather than handing out an exploit against users. The proof-of-concept runs only on data I made up. For anything that warranted private disclosure, the project lists a security contact in its SECURITY.md.

    • 7. What I learned

    • Scanners do not catch everything. IDOR is a logic flaw: the code looks fine, it just forgets an ownership check. That needs a test or a manual review, not a pattern match.
    • A rule is only useful if it stays quiet on safe code. Testing against a fixed version is how you know it will not annoy developers into ignoring it.
    • Good findings tell the developer the fix, not just the problem.
