Building and Securing a Small-Office Network in Cisco Packet Tracer

Medha Holla · Network security · Tools: Cisco Packet Tracer 9.0, Cisco IOS (ISR 4331 router, Catalyst 2960 switch)

Summary. Small offices often run staff computers, a file server and the guest Wi-Fi on one flat network, so a visitor's laptop can reach the server holding client files. I designed the network for a made-up 5-person accounting firm, "Kestrel Accounting", built it in Cisco Packet Tracer, and locked it down.

Staff and guests get separate networks (VLANs) and automatic addresses, both reach the internet through NAT, and the router blocks guests from every staff device. Router admin is SSH only, from the staff network only, with a lockout after 3 wrong passwords. Every staff switch port accepts only its own device.

I then attacked my own network to test each control, and all of them held. Testing also turned up a gap I had missed, a switch with no admin password, which I fixed.

2. Building it

Switch: VLANs, trunk and unused ports

vlan 10
 name STAFF
vlan 20
 name GUEST
vlan 99
 name PARKING
!
interface range fa0/1, fa0/3, fa0/5
 switchport mode access
 switchport access vlan 10
interface fa0/13
 switchport mode access
 switchport access vlan 20
!
interface gig0/1
 switchport mode trunk
 switchport trunk allowed vlan 10,20
 switchport nonegotiate
!
interface range fa0/2, fa0/4, fa0/6 - 12, fa0/14 - 24, gig0/2
 switchport access vlan 99
 shutdown

The trunk only carries VLANs 10 and 20, and nonegotiate stops a device on the other end from talking the port into becoming a trunk (a VLAN-hopping trick). Unused ports are shut down and parked in a VLAN that goes nowhere, so plugging into a spare wall socket gets you nothing.

Router: one sub-interface per VLAN, and DHCP

interface gig0/0/0.10
 encapsulation dot1Q 10
 ip address 192.168.10.1 255.255.255.0
interface gig0/0/0.20
 encapsulation dot1Q 20
 ip address 192.168.20.1 255.255.255.0
!
ip dhcp excluded-address 192.168.10.1 192.168.10.20
ip dhcp excluded-address 192.168.20.1 192.168.20.10
ip dhcp pool STAFF
 network 192.168.10.0 255.255.255.0
 default-router 192.168.10.1
 dns-server 1.1.1.1
ip dhcp pool GUEST
 network 192.168.20.0 255.255.255.0
 default-router 192.168.20.1
 dns-server 1.1.1.1

Both PCs and the guest laptop were set to DHCP and got addresses in the right network straight away (PC0 192.168.10.21, PC1 192.168.10.22, guest laptop 192.168.20.11), which confirmed the VLANs and trunk were working before I added any security.

Router: internet access with NAT

interface gig0/0/1
 description Link to ISP
 ip address 203.0.113.2 255.255.255.252
 ip nat outside
interface gig0/0/0.10
 ip nat inside
interface gig0/0/0.20
 ip nat inside
!
access-list 1 permit 192.168.10.0 0.0.0.255
access-list 1 permit 192.168.20.0 0.0.0.255
ip nat inside source list 1 interface gig0/0/1 overload
ip route 0.0.0.0 0.0.0.0 203.0.113.1

Private 192.168.x.x addresses can't travel across the internet, so the router swaps them for its one public address on the way out (PAT, or NAT "overload") and swaps them back on the way in. To stand in for the internet I added an ISP router and a public web server (198.51.100.10) behind it. The ISP router has no route to the office's private networks, just like a real ISP, so the office can only reach the server if NAT is working.

3. Locking it down

Keep guests away from staff (extended ACL)

ip access-list extended GUEST-IN
 remark Guests cannot reach staff network or router management
 deny ip 192.168.20.0 0.0.0.255 192.168.10.0 0.0.0.255
 deny tcp 192.168.20.0 0.0.0.255 any eq 22
 deny tcp 192.168.20.0 0.0.0.255 any eq 23
 permit udp any any eq bootps
 permit ip 192.168.20.0 0.0.0.255 any
!
interface gig0/0/0.20
 ip access-group GUEST-IN in

The list is applied inbound on the guest sub-interface, so guest traffic is checked the moment it reaches the router. Order matters: the deny lines come first, DHCP is allowed so guests can still get an address, and everything else (the internet) is allowed last.

Router admin: SSH only, staff only, with a lockout

hostname KA-R1
ip domain-name kestrel.local
crypto key generate rsa general-keys modulus 2048
ip ssh version 2
username netadmin privilege 15 secret <hidden>
enable secret <hidden>
service password-encryption
security passwords min-length 10
login block-for 120 attempts 3 within 60
banner motd ^Authorised access only. Activity is monitored.^
!
ip access-list standard MGMT-ONLY
 permit 192.168.10.0 0.0.0.255
 deny any
line vty 0 4
 login local
 transport input ssh
 access-class MGMT-ONLY in
 exec-timeout 5 0
line con 0
 login local
 exec-timeout 5 0
  • SSH version 2 only: Telnet sends passwords in plain text, so it is switched off.
  • Only the staff network can even open a login prompt (access-class), and guests are blocked from ports 22 and 23 by the guest ACL as well.
  • Brute-force protection: 3 failed logins within 60 seconds blocks all logins for 2 minutes.
  • Idle sessions close after 5 minutes, and passwords are stored hashed (secret), not in plain text.

Switch ports: only the right device

interface range fa0/1, fa0/3, fa0/5
 spanning-tree portfast
 switchport port-security
 switchport port-security maximum 1
 switchport port-security mac-address sticky
 switchport port-security violation shutdown

Each staff port learns the MAC address of the first device it sees and saves it (sticky). Any other device on that port shuts the port down. The guest port uses restrict instead, which drops the unknown device's traffic and logs it without taking the port down, since visitors change often.

4. Testing it: attacking my own network

Configuration is only half the job, so I tried to break each control.

Test 1: can a guest reach a staff PC?

C:\>ping 192.168.10.21     (from the guest laptop)
Reply from 192.168.20.1: Destination host unreachable.
Reply from 192.168.20.1: Destination host unreachable.
Reply from 192.168.20.1: Destination host unreachable.
Reply from 192.168.20.1: Destination host unreachable.
    Packets: Sent = 4, Received = 0, Lost = 4 (100% loss)

C:\>ping 192.168.20.1      (its own gateway)
Reply from 192.168.20.1: bytes=32 time<1ms TTL=255  (x4)
    Packets: Sent = 4, Received = 4, Lost = 0 (0% loss)

Blocked. The second ping matters: it proves the guest network itself works, so the block comes from the ACL, not from a broken link.

Test 2: password guessing over SSH

C:\>ssh -l netadmin 192.168.10.1     (from a staff PC)
Password:
% Login invalid
Password:
% Login invalid
Password:
[Connection to 192.168.10.1 closed by foreign host]

C:\>ssh -l netadmin 192.168.10.1     (straight away)
% Connection refused by remote host

After 3 wrong passwords the router dropped the session and then refused every new login for 2 minutes, which makes guessing a password impractical.

Test 3: Telnet

C:\>telnet 192.168.10.1
Trying 192.168.10.1 ...Open
[Connection to 192.168.10.1 closed by foreign host]

Refused. The router closes the connection before ever showing a login prompt, so no password can be sent in plain text.

Test 4: a stranger plugs into a staff port

I unplugged PC1 and connected a different laptop to its switch port, as someone might at an empty desk. The laptop asked for an address and never got one. The switch log:

%PM-4-ERR_DISABLE: psecure-violation error detected on Fa0/3, putting Fa0/3 in err-disable state.
%PORT_SECURITY-2-PSECURE_VIOLATION: Security violation occurred, caused by MAC address
0090.2B86.24CD on port FastEthernet0/3.

KA-SW1#show port-security interface fa0/3
Port Security              : Enabled
Port Status                : Secure-shutdown
Violation Mode             : Shutdown
Maximum MAC Addresses      : 1
Sticky MAC Addresses       : 1
Last Source Address:Vlan   : 0090.2B86.24CD:10
Security Violation Count   : 1

Port shut down and the intruder's MAC address logged.

To restore service I reconnected PC1 and reset the port (shutdown then no shutdown), and PC1 got its usual address back.

Test 5: can both networks reach the internet?

C:\>ping 198.51.100.10     (from staff PC0)
Reply from 198.51.100.10: bytes=32 time<1ms TTL=126  (x4)
    Packets: Sent = 4, Received = 4, Lost = 0 (0% loss)

Staff reach the internet. The guest laptop also opened http://198.51.100.10 in its browser and loaded the server's home page.

Because the ISP router has no route back to 192.168.x.x, these replies can only return through the office router's NAT. So one test proves the routing, the default route and the address translation together, and it shows guests still get internet even though they're cut off from staff. (The very first ping lost 2 packets while the routers learned each other's hardware addresses with ARP; every ping after that was 4 of 4.)

5. The gap testing found

While I was looking at the switch after test 4, I realised I had hardened the router but never set any password on the switch. Anyone with a console cable could have walked up and reconfigured it, for example moving their own port into the staff VLAN. I fixed it:

enable secret <hidden>
username netadmin privilege 15 secret <hidden>
service password-encryption
line con 0
 login local
 exec-timeout 5 0
line vty 0 15
 transport input none

The switch now needs a login on its console and accepts no remote logins at all, since nothing needs to manage it over the network.

7. Problems I hit

  • Switch port numbers didn't match my plan. The cable menu in Packet Tracer only lists free ports, so the list shifted as I connected devices and PC1 landed on Fa0/3 instead of Fa0/2. Fix: I checked which ports were actually up (show interfaces status and the link-up messages) and built the VLAN and port-security config around the real ports, not the plan.
  • Commands typed in user mode failed. show port-security returned "Invalid input" because I was at the > prompt. It needs privileged mode (enable, prompt #).
  • I locked myself out of my own console. After the hardening, the router asked for a username and password on the console too, and the login timed out after 5 minutes while I was away. That's the control working as intended, so rather than weaken it I loaded the NAT settings as a config file through Packet Tracer's "merge running config" option and saved it.
  • no ip http server was rejected by this router image in Packet Tracer. It's harmless here because the simulated router doesn't run a web server, but on real hardware I would make sure the HTTP management page is off.

8. What I'd add next

  • Send logs somewhere central: forward router and switch logs (syslog) to a server, so a port-security violation raises an alert in a SIEM like my Splunk lab instead of sitting in the switch's buffer.
  • DHCP snooping and Dynamic ARP Inspection on the switch, to stop a rogue DHCP server or ARP spoofing inside a VLAN.
  • Automatic recovery for err-disabled ports after a set time, plus a note in the runbook on how staff report a locked port.
  • Wireless: put the guest network on a real access point with WPA3 and client isolation.

9. What I learned

  • Segmentation is the cheapest big win: once guests are in their own VLAN, one ACL line keeps them away from everything that matters.
  • Always prove a block with a matching "allowed" test. A failed ping on its own could just mean a broken network.
  • Testing finds what reviewing misses. I only noticed the unprotected switch because I was poking at it during a test.
