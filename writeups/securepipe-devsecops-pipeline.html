SecurePipe: Break It, Then Make It Unbreakable

Medha Holla · DevSecOps / application security · Tools: Python, FastAPI, Docker, GitHub Actions, Semgrep, Gitleaks, Trivy, Checkov

Summary. I built a small notes API with 9 security flaws planted on purpose, then built a CI/CD pipeline that scans every push and blocks the merge if any of those flaws are present. The pipeline catches all 11: 8 through scanners with custom rules, and 3 through tests and a runtime log scan (the flaws that no static scanner can see, like an access-control gap or personal data leaking into logs). The custom rules raise 0 false positives on a fixed version of the same code.

Why: it shows the full loop a security engineer runs: find the weakness, prove it is real, then automate a control so it cannot come back.

Code and live pipeline: github.com/medhaholla7/securepipe

The app is intentionally vulnerable. It runs only on my own machine and is never deployed to the internet.

1. The app and its planted flaws

A FastAPI "notes" API with SQLite and JWT login. Users log in and read their own notes. I seeded these flaws, each tagged in the code and mapped to a CWE:

#FlawCWECaught by

2CORS allows any origin with credentialsCWE-942Semgrep
3Passwords stored in plain textCWE-256Semgrep

5Any user can read any note by changing the ID (IDOR)CWE-639Access-control test
6Debug endpoint returns all config, including secretsCWE-215Semgrep
7Outdated dependency (PyJWT 1.7.1)CWE-1395Trivy (5 CVEs)
8Secrets committed in a .env fileCWE-798Gitleaks (custom rule)
9Container runs as rootCWE-250Trivy, Checkov

2. Proving the flaws are real

Before writing any detection, I ran the app locally and confirmed each flaw actually worked:

  • IDOR: logged in as bob, requested note 1, and got alice's private note back. The code checked the token was valid but never checked who owned the note.
  • SQL injection: the login built its query with an f-string, so a crafted username logged in without a valid password.
  • Debug leak: /debug returned the signing secret and every environment variable.

3. The pipeline

A GitHub Actions workflow runs 6 jobs on every push and pull request. Any finding fails the build, so the PR cannot be merged. A small script turns each scanner's output into inline annotations, so the developer sees the problem on the exact line of their pull request.

JobToolWhat it checks

4. Writing custom Semgrep rules

I wrote 5 rules, one per code flaw, each with a CWE tag and a message telling the developer how to fix it. For example, the SQL injection rule flags any f-string that starts a SQL statement and contains a variable:

- id: sqli-fstring-execute
  severity: ERROR
  message: SQL built from an f-string (CWE-89). Use parameterised queries.
  pattern-regex: 'f"\s*(SELECT|INSERT|UPDATE|DELETE)[^"]*\{'

To test for false positives, I wrote a fixed copy of the app (parameterised queries, secret from the environment, restricted CORS, no debug endpoint) and ran the same rules against it.

5. Results (from real pipeline runs)

  • All 9 planted flaws caught: 8 by scanners, and the IDOR by the access-control test.
  • 0 false positives from my custom Semgrep rules on the fixed code.
  • Trivy found 5 known CVEs in the old PyJWT version (1 critical, 4 high), including authentication bypass with forged tokens.
  • Privacy: a custom rule and a runtime log scan caught passwords, emails and phone numbers written to logs, each mapped to the GDPR article it breaks (data minimisation and security of processing). The scan masks the value it finds, so it never re-leaks the data.

6. Problems I hit and how I solved them

  • Gitleaks missed every planted secret. Its default rules only recognise real provider key formats (AWS, GitHub and so on), not a hand-written signing key or a password in a .env file. I wrote 2 custom rules, which caught all 3.
  • Gitleaks only checked new commits. The GitHub Action scanned just the commits in each push, so a secret added earlier was never checked. I switched to scanning the full git history on every run, because a secret deleted later is still leaked.
  • A rule labelled the wrong flaw. My "hardcoded secret" rule fired on the SQL line, because password='{body.password}' looks like a password. It is a placeholder, not a secret, so I tightened the pattern.
  • Rules that didn't fire. My first SQL injection and CORS rules used Semgrep's code-structure patterns, which were too strict. I switched them to regex patterns and tested until all 5 fired.
  • The Trivy job broke at setup. The version of the Trivy GitHub Action I pinned no longer existed. I replaced it with a pinned Trivy release.

7. What I learned

  • Scanners do not catch everything. IDOR is a logic flaw: the code looks fine, it just forgets an ownership check. That needs a test or a manual review, not a pattern match.
  • A rule is only useful if it stays quiet on safe code. Testing against a fixed version is how you know it will not annoy developers into ignoring it.
  • Good findings tell the developer the fix, not just the problem.

8. Next steps

Add container image signing and a software bill of materials (SBOM) so the supply chain itself is verifiable, not just the code.
