SecurePipe: Break It, Then Make It Unbreakable

Medha Holla · DevSecOps / application security · Tools: Python, FastAPI, Docker, GitHub Actions, Semgrep, Gitleaks, Trivy, Checkov

Summary. I built a small notes API with 9 security flaws planted on purpose, then built a CI/CD pipeline that scans every push and blocks the merge if any of those flaws are present. I wrote 5 custom Semgrep rules that catch 5 of the 9 flaws with 0 false positives on a fixed version of the same code.

Why: it shows the full loop a security engineer runs: find the weakness, prove it is real, then automate a control so it cannot come back.

The app is intentionally vulnerable. It runs only on my own machine and is never deployed to the internet.

1. The app and its planted flaws

A FastAPI "notes" API with SQLite and JWT login. Users log in and read their own notes. I seeded these flaws, each tagged in the code and mapped to a CWE:

#FlawCWECaught by
1Hardcoded JWT signing secretCWE-798Semgrep, Gitleaks
2CORS allows any origin with credentialsCWE-942Semgrep
3Passwords stored in plain textCWE-256Semgrep
4SQL injection in the login queryCWE-89Semgrep
5Any user can read any note by changing the ID (IDOR)CWE-639Manual test
6Debug endpoint returns all config, including secretsCWE-215Semgrep
7Outdated dependency (PyJWT 1.7.1)CWE-1395Trivy
8Secrets committed in a .env fileCWE-798Gitleaks
9Container runs as rootCWE-250Trivy, Checkov

2. Proving the flaws are real

Before writing any detection, I ran the app locally and confirmed each flaw actually worked:

  • IDOR: logged in as bob, requested note 1, and got alice's private note back. The code checked the token was valid but never checked who owned the note.
  • SQL injection: the login built its query with an f-string, so a crafted username logged in without a valid password.
  • Debug leak: /debug returned the signing secret and every environment variable.

3. The pipeline

A GitHub Actions workflow runs four scanners on every push and pull request. Any finding fails the build, so the PR cannot be merged.

JobToolWhat it checks
SecretsGitleaksKeys and passwords committed anywhere in git history
Code (SAST)SemgrepInsecure code patterns, using my custom rules plus the standard Python ruleset
Dependencies and containerTrivyKnown vulnerable packages and container misconfigurations (HIGH and CRITICAL only)
Infrastructure as codeCheckovDockerfile and Compose misconfigurations

4. Writing custom Semgrep rules

I wrote 5 rules, one per code flaw, each with a CWE tag and a message telling the developer how to fix it. For example, the SQL injection rule flags any f-string that starts a SQL statement and contains a variable:

- id: sqli-fstring-execute
  severity: ERROR
  message: SQL built from an f-string (CWE-89). Use parameterised queries.
  pattern-regex: 'f"\s*(SELECT|INSERT|UPDATE|DELETE)[^"]*\{'

To test for false positives, I wrote a fixed copy of the app (parameterised queries, secret from the environment, restricted CORS, no debug endpoint) and ran the same rules against it.

5. Results

  • Vulnerable app: 7 findings covering 5 of the 9 planted flaws.
  • Fixed app: 0 findings, so 0 false positives.
  • The remaining flaws are covered by Gitleaks (committed secrets), Trivy (outdated dependency, root container) and Checkov.

6. Problems I hit and how I solved them

  • Rules that didn't fire. My first SQL injection and CORS rules used Semgrep's code-structure patterns, which were too strict and matched nothing. I switched those two to regex patterns and tested again until all 5 fired.
  • Semgrep hanging. Semgrep tried to contact its server for metrics and version checks and timed out on my network. Running it with --metrics=off fixed it.

7. What I learned

  • Scanners do not catch everything. IDOR is a logic flaw: the code looks fine, it just forgets an ownership check. That needs a test or a manual review, not a pattern match.
  • A rule is only useful if it stays quiet on safe code. Testing against a fixed version is how you know it will not annoy developers into ignoring it.
  • Good findings tell the developer the fix, not just the problem.

8. Next steps

Add an automated test that catches the IDOR, and a privacy check that flags personal data (emails, phone numbers) written to logs, mapped to the relevant GDPR articles.
