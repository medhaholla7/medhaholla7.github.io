Detecting Credential Stuffing and Account Takeover with Splunk

Medha Holla · Detection engineering · Tools: Python, Splunk Enterprise 10.6, Ubuntu Server (home SOC lab)

Summary. Retailers with loyalty schemes are a favourite target for credential stuffing: attackers take email and password pairs leaked from other websites and try them on a new site, betting that some customers reused their password. If one works, they take over the account and spend the points.

I built a realistic login log for a made-up loyalty website, "Kestrel Rewards", containing a day of normal customer logins plus a night-time bot attack. I loaded it into my home Splunk server and wrote three detections. Together they found all 30 attacking IP addresses, all 4 hijacked accounts, and every action the attacker took afterwards, with no normal customers flagged.

Attack techniques: credential stuffing (MITRE ATT&CK T1110.004), use of valid accounts (T1078), account manipulation (T1098).

1. Why this attack is different from brute force

In my first SOC lab writeup I caught a brute-force attack: one IP trying many passwords against one account. I noted that this rule would miss an attacker who tries many different accounts once each. Credential stuffing is exactly that:

Brute forceCredential stuffing
TargetOne accountThousands of accounts
PasswordsGuessedReal, leaked from other sites
Failures per accountManyUsually one, so per-account lockouts never trigger
Signal to look forMany failures on one accountOne IP touching many different accounts

2. The data

Real customer login data is private, so I generated a synthetic dataset with a short Python script. It writes one JSON event per login with the time, source IP, username, result and browser (user agent). It contains 1,692 events:

TrafficWhat happensEvents
Normal customers200 customers log in 1 to 3 times between 7am and 11pm from their home IP, sometimes mistyping their password once424
The attackFrom 02:00 to 02:42, 30 bot IPs work through a list of 1,260 leaked email and password pairs, one attempt every 2 seconds, using a Python HTTP library as the browser1,260
Takeover4 real customers had reused their password, so the bots got in, changed the account email 3 minutes later, then redeemed the points8

A sample attack event:

{"time": "2026-10-14T02:00:00", "src_ip": "45.126.196.49", "user": "leaked0666@mail.com",
 "action": "login", "result": "unknown_user", "user_agent": "python-requests/2.31"}

Most of the leaked emails (1,200) don't belong to Kestrel customers at all, so they fail with unknown_user. That alone is a strong clue: real customers know their own email address.

Getting it into Splunk

I copied the file to my Splunk server over SSH and indexed it once as JSON, so Splunk extracts every field automatically:

scp -P 2222 rewards_logins.json medha@127.0.0.1:/tmp/
sudo -u splunk /opt/splunk/bin/splunk add oneshot /tmp/rewards_logins.json -index main -sourcetype _json

3. Detection 1: one IP, many accounts

index=main source="*rewards_logins.json" action=login result!=success
| stats dc(user) as accounts_tried by src_ip
| where accounts_tried>=10
| sort - accounts_tried

dc(user) counts the distinct accounts each IP failed on. A customer who mistypes their password fails on one account (their own), so the highest count for any normal IP was 1. Every bot IP failed on 41 or 42 different accounts:

    src_ip     accounts_tried
-------------- --------------
45.12.244.180              42
45.124.61.181              42
...                       ...
45.126.196.49              41
45.16.44.92                41
45.227.182.37              41
45.67.64.247               41

Result: 30 of 30 attacking IPs found, 0 normal customers flagged. The gap between normal (1) and attack (41+) is so wide that a threshold of 10 leaves plenty of room either side.

The four IPs at 41 instead of 42 stood out: each had one attempt that didn't fail. That led to the next detection.

4. Detection 2: account takeover

An IP that fails on many accounts and then succeeds on one has almost certainly found a reused password. This search looks for exactly that pattern:

index=main source="*rewards_logins.json" action=login
| stats dc(eval(if(result!="success",user,null()))) as failed_accounts
        values(eval(if(result=="success",user,null()))) as compromised_user
        by src_ip
| where failed_accounts>=10 AND isnotnull(compromised_user)
   src_ip     failed_accounts   compromised_user
------------- --------------- --------------------
45.126.196.49              41 customer140@mail.com
45.16.44.92                41 customer191@mail.com
45.227.182.37              41 customer109@mail.com
45.67.64.247               41 customer120@mail.com

Result: all 4 hijacked accounts identified, with the IP that took each one. This is the higher-priority alert, because it means real customers have already lost control of their accounts.

5. Detection 3: what the attacker did next

index=main source="*rewards_logins.json" (action=change_email OR action=redeem_points)
| table _time src_ip user action user_agent
           _time               src_ip             user            action          user_agent
--------------------------- ------------- -------------------- ------------- --------------------
2026-10-14 02:37:34.000 UTC 45.227.182.37 customer109@mail.com change_email  python-requests/2.31
2026-10-14 02:39:34.000 UTC 45.227.182.37 customer109@mail.com redeem_points python-requests/2.31
...

Every compromised account followed the same playbook: log in, change the email 3 minutes later so password-reset emails go to the attacker, then spend the points 2 minutes after that. All of it came from the attacking IP and the python-requests user agent, which no real customer uses.

6. Making it automatic

I saved detections 1 and 2 as scheduled Splunk alerts that run every hour over the last hour of logs: Credential stuffing: one IP, many accounts (high severity) and Account takeover after credential stuffing (critical).

7. If this were real: response

  1. Protect the 4 customers first: lock the accounts, reverse the email changes, restore the points, and contact each customer through their original email to reset their password.
  2. Block the 30 IPs at the web application firewall, and rate-limit login attempts per IP.
  3. Reset anyone else at risk: the 56 real customers whose emails appeared in the attack with a wrong password were targeted too. Prompt them to change their password.
  4. Make stuffing harder: add bot detection or a challenge after repeated failures from one IP, check new passwords against known breach lists, and offer multi-factor authentication.
  5. Require re-authentication for sensitive actions like changing the email or redeeming points, which would have stopped the takeover even after login.

8. Problems I hit and how I solved them

  • Splunk wasn't running after my VM had frozen earlier in the day. The CLI said splunkd is unreachable. Fix: started it again and checked it with the web interface message.
  • Splunk refused to start with sudo because running it as root is deprecated. Fix: run it as the account that owns the install (sudo -u splunk), which is also the least-privilege choice.
  • A script couldn't find my Splunk server on the usual VirtualBox host-only network. My VM actually uses NAT with port forwarding (SSH on 2222), so Splunk's management port wasn't reachable from Windows. Fix: copied the file in over SSH with scp -P 2222 and ran Splunk's own CLI on the server instead.
  • Watch the source path: a oneshot upload records the full path (/tmp/rewards_logins.json), so searches use the wildcard source="*rewards_logins.json".

9. What I'd improve next

  • Catch slow, distributed attacks: an attacker using thousands of IPs with one attempt each would slip under detection 1. Next I'd alert on a site-wide spike in unknown_user failures, which doesn't depend on the IP.
  • Add a time window (for example 10 minutes) so the rules work on live, continuous data.
  • Flag new-device takeovers: an email change from an IP or user agent the customer has never used before.

10. What I learned

  • Counting distinct accounts per IP instead of failures per account is what separates credential stuffing from normal forgotten passwords.
  • One detection often points to the next: the IPs with one fewer failure were the ones that got in.
  • The real damage happens after the login, so watching what accounts do next (email changes, point redemptions) matters as much as watching the login itself.
