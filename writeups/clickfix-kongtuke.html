Investigating a ClickFix Malware Infection with Wireshark

Medha Holla · Network forensics · Evidence: one packet capture (73,779 packets, 21 minutes) from the malware-traffic-analysis.net exercise of 11 Sep 2026

Summary. A company laptop was infected after the user visited a hacked website that showed a fake "verify you are human" page. The page tricked the user into pasting a malicious command into Windows (a technique called ClickFix, used by the KongTuke campaign).

I identified the infected laptop and user, rebuilt the attack step by step, and found the malware contacting the attacker's server every 10 seconds, including one 4.4 MB upload that was likely stolen data.

Verdict: confirmed compromise. Isolate the laptop and reset the user's password.

How I worked it out

  • IP: the network was 10.9.11.0/24. Apart from the gateway (.1) and domain controller (.2), the only address inside it was .135, and it carried almost all the traffic.
  • Host name: Windows PCs announce their name to the whole network. The browser filter showed 10.9.11.135 announcing itself as DESKTOP-6T17ZFM. (dhcp and nbns returned nothing, because the laptop was already set up before the capture started.)
  • User: in a Windows domain, logins go through Kerberos and the username is sent in plain text. Every login showed gmcdowell. It has no $ on the end, so it is a person, not a computer account.
  • Full name: the laptop asked the domain controller for the user's profile (SAMR, operation 36). The reply contained "Gabriel McDowell".

2. What happened

I listed every website the laptop contacted, in order, using the site names visible at the start of encrypted connections (tls.handshake.extensions_server_name) and plain web requests (http.request).

Time (UTC)Event
20:05:55User visits quadcinema[.]com, a real site that had been hacked.
20:05:56The page loads a hidden script from aatthews[.]cfd, which shows the fake verification page.
20:06:3335 seconds later, a burst of new random-looking domains (winrun2915[.]com, logincrypt8338[.]com, opscast3707[.]net). This is when the user ran the pasted command.
20:06:42Laptop contacts xos-aploq[.]com, which delivers the malware.
20:06:4736 MB downloaded from nodejs[.]org. The malware is written in JavaScript and brings its own Node.js to run.
20:06:57Malware starts contacting the attacker's server know.mom-nower[.]com (86.106.87[.]134) every 10 seconds.
20:10:034.4 MB upload to the attacker's server. Likely stolen data.
20:22:17Malware switches to backup servers (comonto-rsr[.]com, fif-lost[.]com, bert-hits[.]com).
20:27:05Capture ends. The laptop is still infected and still reporting in.

Why I concluded it was command-and-control (C2) traffic

  • Clockwork timing: a request almost exactly every 10 seconds. People don't browse like that; malware checking for orders does.
  • Plain HTTP to an odd domain: most real sites use HTTPS.
  • Empty replies: the server usually answered "204 No Content", meaning "no orders yet".
  • Fake identity: the requests claimed to be Firefox, but they came from the malware.
  • One big upload: normal check-ins were a few hundred bytes; one was 4.4 MB.

4. Recommended response

  1. Contain: disconnect DESKTOP-6T17ZFM from the network.
  2. Reset: change gmcdowell's password and end all their sessions. Treat saved browser passwords as stolen.
  3. Block: add the indicators above to the firewall and DNS blocklists.
  4. Hunt: check logs for any other machine contacting these domains or downloading Node.js unexpectedly.
  5. Rebuild: reinstall the laptop rather than trying to clean it.
  6. Prevent: teach staff that no real website asks you to paste commands into Windows.

5. What I learned

  • Windows domain traffic (Kerberos, SAMR, browser announcements) reveals who a machine and user are, even when the obvious sources are empty.
  • Timing is evidence: the 35-second gap and the steady 10-second rhythm told the story better than any single packet.
  • Legitimate sites like nodejs.org can still be part of an attack. Context matters.
