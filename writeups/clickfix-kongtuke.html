Investigating a ClickFix Malware Infection with Wireshark

Medha Holla Evidence: packet capture (pcap), 73,779 packets, 21 minutes Source: malware-traffic-analysis.net exercise, 11 Sep 2026
wiresharkclickfixkongtuke active-directorykerberosc2-beaconing
summary.txt_▢✕

A Windows workstation in the overhands[.]org Active Directory domain was infected after its user visited a website that served a fake "verify you are human" page. The page used the ClickFix technique: it tricked the user into pasting a malicious command into the Windows Run box.

From the packet capture I identified the infected host (DESKTOP-6T17ZFM, user gmcdowell), reconstructed the infection chain, and found the malware beaconing to a command-and-control (C2) server every 10 seconds, including one 4.4 MB upload that is likely stolen data.

Verdict: confirmed compromise. The host should be isolated and the user's credentials treated as stolen.

investigation.log_▢✕

1. Finding the infected machine

I started with Statistics > Endpoints > IPv4 to see every address in the capture. Inside the LAN range there were only three: the gateway (.1), the domain controller (.2) and 10.9.11.135. The broadcast address (.255) is not a host. That left 10.9.11.135 as the client, and it had by far the most traffic.

To get its hardware address I filtered for its outgoing traffic and read the Ethernet header:

ip.src == 10.9.11.135

Source MAC: 08:d4:0c:7a:29:1e. The first half (08:d4:0c) belongs to Intel, so it is a normal Intel network card.

Getting the host name

My first attempts (dhcp and nbns) returned nothing useful, because the machine already had its address before the capture started. What worked was the Windows browser protocol, which computers use to announce themselves on the network:

browser

The Info column showed Request Announcement DESKTOP-6T17ZFM coming from 10.9.11.135. The only other name announced was WIN-GTWXC9UYSE4, which is the domain controller. The same host name also appears in Kerberos traffic as the service host/desktop-6t17zfm.overhands.org.

Getting the user account

In an Active Directory network, users log in through Kerberos, and the client name is sent in plain text:

kerberos.CNameString

Every request showed gmcdowell. It has no $ at the end, so it is a person's account, not a computer account.

Getting the full name

The client also asked the domain controller about the user's account through SAMR, the Windows protocol for account lookups. I filtered for QueryUserInfo requests (operation number 36):

samr.opnum == 36

Inside the QueryUserInfo response (packet 70694), the Full Name field reads Gabriel McDowell. My first attempt picked up a group lookup ("Domain Computers") instead, which taught me to check the operation type before trusting a field.

2. Reconstructing the infection

With the victim identified, I looked at what the machine contacted and in what order, using DNS queries, TLS server names and HTTP requests:

dns.flags.response == 0
tls.handshake.extensions_server_name
http.request

The fake verification page

The capture starts with the user browsing to quadcinema[.]com. Less than a second later the browser loaded content from aatthews[.]cfd, an unrelated domain on a cheap top-level domain. This matches how KongTuke works: a legitimate but compromised site loads a script that shows the fake verification page.

The ClickFix command runs

About 35 seconds later, the machine suddenly contacted a burst of new domains: winrun2915[.]com, logincrypt8338[.]com, opscast3707[.]net and then three subdomains of xos-aploq[.]com. That gap fits the time a user needs to open the Run box, paste the command and press Enter. opscast3707[.]net alone sent the host about 7.5 MB.

Malware sets up its runtime

Seconds later the host downloaded about 36 MB from nodejs[.]org and later contacted registry.npmjs[.]org. Both are legitimate sites, but a normal user does not download Node.js in the middle of an infection chain. This suggests the malware is written in JavaScript and brings its own Node.js runtime to run it.

Command-and-control beaconing

From 20:06:57 onwards, the host sent HTTP requests to know.mom-nower[.]com (86.106.87[.]134) almost exactly every 10 seconds for the rest of the capture:

http.host contains "mom-nower"
  • Regular timing: a steady 10-second rhythm is typical of malware checking in for instructions, not of a person browsing.
  • Plain HTTP with random-looking URLs: each path is random, but they all share the same long hex identifier, which marks this infected host to the attacker.
  • Mostly empty replies: the server usually answered 204 No Content, meaning "nothing to do yet".
  • Fake browser identity: requests claim to come from Firefox 137, but they come from the malware.

At 20:10:03 the host sent a single POST of 4.4 MB to the C2 server. The other check-ins are only a few hundred bytes, so this upload is very likely stolen data such as saved browser credentials or files.

C2 rotation

Around 20:22 the malware started posting to a new set of domains: comonto-rsr[.]com, fif-lost[.]com and bert-hits[.]com, spread over several IP addresses. Each got a small request followed by about 26 KB of data. It also tried globalcert8618[.]net, opsbox8097[.]com and hostjob3862[.]net, which no longer existed (DNS returned "no such domain"). Having many backup domains is a common way for malware to survive when defenders block one.

recommendations.txt_▢✕
  1. Contain: isolate DESKTOP-6T17ZFM from the network straight away.
  2. Credentials: reset gmcdowell's domain password and sign them out of all sessions. Assume any passwords saved in the browser are stolen, because of the 4.4 MB upload.
  3. Block: add the domains and IPs above to the firewall, proxy and DNS blocklists.
  4. Hunt: search proxy and DNS logs for any other host contacting these indicators, and for other machines downloading Node.js unexpectedly.
  5. Recover: reimage the machine rather than trying to clean it.
  6. Prevent: train staff that no real website asks them to paste commands into Run or PowerShell, and consider restricting the Run dialog through Group Policy for standard users.
lessons.txt_▢✕
  • Identity lives in Windows domain protocols. Kerberos, SAMR and the browser protocol answered who, where the obvious ones (DHCP, NBNS) came up empty.
  • Timing is evidence. The 35-second gap before the burst of new domains, and the exact 10-second beacon, told the story more clearly than any single packet.
  • Legitimate sites can be part of an attack. Node.js and npm are safe services, but their appearance in this sequence was a strong clue.
